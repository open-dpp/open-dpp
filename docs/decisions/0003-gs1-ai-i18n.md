# ADR 0003: GS1 AI description translations (de + en) as a generated module

**Status:** Accepted (2026-07-06)

## Context

The AI browser at ref.gs1.org carries translated AI descriptions in 13+ languages. They are
not available via the JSON or JSON-LD endpoints (verified: zero `@language` tags) — they
exist only as a tab-separated block embedded in the page HTML, maintained by GS1 from a
translation spreadsheet. Its keys are **not** 1:1 with AIs:

- decimal-place families collapse the fourth digit to `n` (`390n` covers 3900-3903),
- UI strings use `note-*` keys (ignored by our generator),
- individual cells can be untranslated (e.g. German for 401 GINC falls back to English text).

`@open-dpp/dto` compiles to CJS with no tree-shaking; the table (90 KB) and constants
(56 KB) already ship to the browser. All 15 language columns would add ~300 KB to every
client bundle.

## Decision

- Generate `gs1-ai-i18n.ts` next to the table, exported through the package barrel like the
  other GS1 modules.
- **Languages: `de` and `en` only** (the open-dpp UI languages), ~40-50 KB. Adding a
  language later is a generator flag + rerun.
- **Keys are vendored as published** (family keys like `390n` stay collapsed; `note-*` rows
  dropped). A resolver does the mapping:

  ```ts
  getGs1AiDescription(ai: string, lang: "de" | "en"): string | undefined
  ```

  Lookup chain: exact AI key → family key (trailing digit collapsed to `n`) → `en` fallback
  for untranslated cells → `undefined`. Callers use the table's English `title` as the last
  resort.

## Consequences

- Smallest artifact that mirrors upstream truth; no string duplication across family AIs.
- Consumers get one documented lookup function instead of indexing a map with surprise key
  shapes.
- The extraction depends on the page's embedded TSV (see ADR 0001's drift stance: manual
  regeneration, generator fails loudly if the page structure changes).
