# CI security tooling for a pnpm/Turborepo + Docker + GitHub Actions monorepo

Research ticket [#778](https://github.com/open-dpp/open-dpp/issues/778) of map [#772](https://github.com/open-dpp/open-dpp/issues/772).
Feeds [#791](https://github.com/open-dpp/open-dpp/issues/791) (implement CI gates in advisory mode).
Researched 2026-09-03 against primary sources only (GitHub Docs, GitHub Changelog, tool READMEs/docs, tool source). Every claim carries its source; "not confirmed" means the primary source read did not state it.

## Question

Which tools should implement the plan's automated Controls for this public repo (pnpm 11 + Turborepo, NestJS/Vue, multi-arch Docker images on ghcr.io, GitHub Actions)? For SAST, dependency audit, secret scanning, container scanning, SBOM, DAST, OpenSSF Scorecard, action pinning and image provenance: what does each detect, what does it cost for a public repo, how noisy is it, how is it run advisory-first and later flipped to blocking on High/Critical, and what are the pnpm/monorepo gotchas?

### Where the repo stands (grounding, worktree at `9c560822`; security-relevant files identical on `origin/main`)

- Workflows: `build.yml` (lint, test, multi-arch build → push-by-digest → manifest merge → demo deploy), `e2e.yml` (compose stack `docker-compose.dev.yml` + Playwright), `docs.yml`, `release.yml` (changesets). Only `release.yml` pins actions to SHAs with `# vX.Y.Z` comments; `build.yml`, `e2e.yml`, `docs.yml` use mutable tags (`actions/checkout@v4`, `docker/build-push-action@v6`, `actions/setup-node@v6`, ...).
- `build.yml` grants `packages: write` at workflow level and also builds/pushes images on `pull_request`.
- `Dockerfile`: `node:25-slim` (mutable tag) build + production stages; production stage carries only `pnpm deploy --filter=@open-dpp/main --prod` output plus the client bundle. Compose files reference `mongo:7.0`, `axllent/mailpit:latest`, `quay.io/minio/minio:latest`, `minio/mc:latest`, `ajilaag/clamav-rest` (untagged).
- `.github/dependabot.yml`: `npm`, `docker`, `docker-compose` at `/`, daily. No `github-actions` ecosystem.
- GitHub settings (REST, 2026-09-03): public repo; CodeQL **default setup** already configured (languages `actions`, `javascript-typescript`; `default` suite; weekly; last analysis on `main` today: 87 JS/TS rules, 17 `actions` rules); secret scanning **enabled**; push protection **disabled**; non-provider patterns and validity checks disabled; Dependabot alerts + security updates enabled. Ruleset `protect-main` (active) has `deletion`, `non_fast_forward`, `pull_request` (0 required approvals) and **no required status checks / no code-scanning rule** — so today no CI check can block a merge even if it fails.
- Backlog calibration (numbers kept out of this public file; see the private pre-baseline issue): a double-digit Dependabot backlog exists, dominated by `pnpm-lock.yaml` entries that fan out one alert per resolved version of the same package, and with build-time-only packages labelled `runtime`. The CodeQL `actions` default suite reports **zero** findings although three workflows use mutable tags — the "Unpinned tag" query is evidently not in the `default` suite (see B1).
- No `SECURITY.md`, no `CODEOWNERS`; GitHub detects the licence as AGPL-3.0 while `package.json` says `LGPL-3.0-only` (matters for licence gates, see Open questions).

## Short answer

Recommended stack, cheapest-first, all free for a public repo, all runnable advisory-first:

| Layer                  | Tool                                                                                                                     | One line                                                                                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SAST                   | **CodeQL default setup** (already on)                                                                                    | Keep; gate later with a ruleset `code_scanning` rule (`security_alerts_threshold: high_or_higher`); consider `security-extended` for the `actions` language.                                 |
| Dependency alerts      | **Dependabot** (already on)                                                                                              | Add `github-actions` ecosystem, `groups` + `cooldown`; rely on GitHub preset auto-triage; alerts are the Review Run's dependency evidence.                                                   |

| PR dependency diff     | **`actions/dependency-review-action`**                                                                                   | `warn-only: true` → later `fail-on-severity: high`; docs say free for public repos (one GitHub table disagrees).                                                                             |
| Secrets (server side)  | **GitHub push protection** (free, currently off)                                                                         | Flip the repo switch; it is the only _preventive_ control in this list.                                                                                                                      |
| Secrets (CI)           | **gitleaks CLI** (not `gitleaks-action`)                                                                                 | The action needs an organisation licence key; the MIT CLI does not. `--exit-code 0` + SARIF upload now, `--exit-code 1` later.                                                               |

| SBOM                   | **syft** via `anchore/sbom-action` (CycloneDX JSON) for `pnpm-lock.yaml` and for the image                               | Auto-attaches to GitHub releases; upload as workflow artifact per run. `@cyclonedx/cyclonedx-npm` is npm-only; cdxgen works but is heavier.                                                  |

Blocking, when the baseline triage is done, is a **ruleset** change, not a workflow change: add the check names to `required_status_checks` and a `code_scanning` rule per SARIF-producing tool — the current ruleset has neither.

## Findings

### A. GitHub Advanced Security features for a public repo

- Free on public repos (GitHub's availability table): code scanning, CodeQL CLI, Copilot Autofix, secret scanning, push protection. Paid even on public repos ("with GitHub Code Security / Secret Protection" column only): security campaigns, security overview, custom patterns, AI-detected (Copilot) secrets, delegated bypass, custom Dependabot auto-triage rules. Source: <https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security>
- Billing page: "All public repositories have access to code scanning, secret scanning, and dependency review." <https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-advanced-security/about-billing-for-github-advanced-security>
- Conflict to note: the availability table marks _dependency review_ and _custom auto-triage rules_ as not available on public repos without Code Security; the billing page, the dependency-review page ("available for all public repositories") and the auto-triage page ("available on public repositories") say they are. Two of three pages say free; verify by enabling. Sources: <https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-dependency-review>, <https://docs.github.com/en/code-security/dependabot/dependabot-auto-triage-rules/about-dependabot-auto-triage-rules>
- Validity checks are not free: "only available to users with GitHub Team or GitHub Enterprise who enable the feature as part of GitHub Secret Protection." <https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns>
- Third-party SARIF upload is not restricted for public repos: "For private and internal repositories, code scanning is available when GitHub Code Security features are enabled." <https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github>

### B. SAST — CodeQL code scanning

1. **Detects.** JS/TS security queries (87 rules in the current default run) and, with the `actions` language, workflow issues: code injection, cache/artifact poisoning, untrusted checkout in privileged context, excessive/unmasked secret exposure, "Unpinned tag for a non-immutable Action or reusable workflow", "Use of a known vulnerable action", missing `permissions`. Which of these are in the `default` suite is not documented; the repo's default `actions` run reports 0 findings despite three workflows with mutable tags, so pinning is _not_ covered by the default suite. Query index: <https://codeql.github.com/codeql-query-help/actions/>. Language IDs and build modes: <https://docs.github.com/en/code-security/code-scanning/creating-an-advanced-setup-for-code-scanning/customizing-your-advanced-setup-for-code-scanning>
2. **Default vs advanced setup.** Default setup picks languages, suite (`default` or `security-extended` selectable in the UI) and triggers; advanced setup (workflow with `github/codeql-action`) is needed for custom query packs, `security-and-quality`, or per-language build modes. JS/TS uses build mode `none` (no build). <https://docs.github.com/en/code-security/code-scanning/introduction-to-code-scanning/about-code-scanning-with-codeql>, <https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/manage-your-configuration/edit-default-setup>
3. **Noise.** "The queries in the `default` query suite are highly precise and return few false positive code scanning results." `security-extended` "may return a greater number of false positive code scanning results." <https://docs.github.com/en/code-security/code-scanning/managing-your-code-scanning-configuration/codeql-query-suites>
4. **PR surfacing / default failure rule.** Results appear as the "Code scanning results" check, as annotations on changed files, and in the Security tab. "If the code scanning results check finds any problems with a severity of `error`, `critical`, or `high`, the check fails". Alerts carry a severity (`error`/`warning`/`note`) and a security severity (`critical`/`high`/`medium`/`low`, derived from CVSS of related CVEs). Dismissal reasons: `false positive`, `won't fix`, `used in tests`, `mitigated`, with a ≤280-char comment on the alert timeline. <https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-code-scanning-alerts/triage-alerts-in-pull-requests>, <https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/about-code-scanning-alerts>, <https://docs.github.com/en/rest/code-scanning/code-scanning?apiVersion=2022-11-28>
5. **Advisory → blocking.** Advisory = leave the check unrequired (the current ruleset requires nothing). Blocking = ruleset rule **Require code scanning results**: per tool `alerts_threshold` ∈ `none|errors|errors_and_warnings|all` and `security_alerts_threshold` ∈ `none|critical|high_or_higher|medium_or_higher|all`; merge is blocked when a required tool finds an alert at the threshold, its analysis is still running, or it is not configured. <https://docs.github.com/en/code-security/code-scanning/managing-your-code-scanning-configuration/set-code-scanning-merge-protection>, <https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28>
6. **SARIF upload (used by every other SARIF tool below).** `github/codeql-action/upload-sarif` inputs: `sarif_file`, `category` (distinguishes analyses of the same commit), `wait-for-processing` (default true); needs `security-events: write` (plus `actions: read`/`contents: read` only for private repos). Limits: 20 runs per file, 25 000 results per run (top 5 000 kept by severity), 10 MB gzipped; dedup via `partialFingerprints`. Third-party results "may not include all of the properties" of CodeQL alerts — check that each tool's SARIF carries `security-severity`, otherwise the ruleset security threshold cannot see it. <https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning>, <https://raw.githubusercontent.com/github/codeql-action/main/upload-sarif/action.yml>

### C. Dependency audit

**C1. Dependabot alerts / security updates / version updates (free, already partly on)**

- Alerts come only from GitHub-reviewed advisories; severity is CVSS-based (`low/medium/high/critical`; CVSS 3.1 and 4.0 supported); EPSS shown. Scope detection (`development` vs `runtime`) is documented as supported for `pnpm-lock.yaml`, but in this repo build-time-only packages are labelled `runtime` (observed), so do not trust the scope filter for the blocking decision. <https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts>, <https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-manifests-for-dependency-scope>
- GitHub preset auto-triage ("Dismiss low impact issues for development-scoped dependencies") is "enabled by default for public repositories"; custom rules (≤10, targets CVE/CWE/scope/severity/EPSS/manifest, actions dismiss or open PR) — availability conflict, see A. <https://docs.github.com/en/code-security/dependabot/dependabot-auto-triage-rules/customizing-auto-triage-rules-to-prioritize-dependabot-alerts>
- Version updates: pnpm is supported via `package-ecosystem: npm` (pnpm v7–v10 listed; an explicit pnpm-_workspace_ statement is not confirmed); `github-actions`, `docker` and `docker-compose` supported (docker/compose: version updates only, no security updates). Options worth adding: `groups` (with `applies-to: security-updates` for grouped security PRs), `cooldown` (default 3 days for version updates, never for security updates; `default-days`, `semver-*-days`). <https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories>, <https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference>
- For SHA-pinned actions Dependabot updates the SHA _and_ the `# vX.Y.Z` comment (Changelog 2022-10-31), but "will not create alerts for actions pinned to SHA values" — pinning trades alerting for immutability; the `github-actions` ecosystem is therefore mandatory once pins exist. <https://github.blog/changelog/2022-10-31-dependabot-now-updates-comments-in-github-actions-workflows-referencing-action-versions/>, <https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions>
- Where results surface: Security → Dependabot; REST `GET /repos/{o}/{r}/dependabot/alerts?state=open` (fields `security_advisory.severity`, `dependency.scope`, `dependency.manifest_path`).

**C2. `pnpm audit` (built in; no licence)**

- Queries the registry's `/-/npm/v1/security/advisories/bulk` endpoint; `--audit-level low|moderate|high|critical` ("Only print advisories with severity greater than or equal to"), `--prod`/`--dev`, `--no-optional`, `--json`, `--ignore-registry-errors` (exit 0 on non-200), `--ignore <GHSA>`, `--ignore-unfixable`, `--fix` (writes `overrides` to `pnpm-workspace.yaml`; `--fix=update` bumps the lockfile instead). Ignore list lives in `pnpm-workspace.yaml` under `audit.ignore` (older: `auditConfig.ignoreGhsas`); CVE ids are no longer accepted. <https://pnpm.io/cli/audit>
- Exit code (from source, `pnpm11/deps/compliance/commands/src/audit/audit.ts`): advisories are filtered by `AUDIT_LEVEL_NUMBER[severity] >= auditLevel` after removing ignored GHSAs, and `exitCode` is 1 iff any remain — so `pnpm audit --audit-level high` is already a High/Critical gate. `recursiveByDefault = true`: it audits the whole workspace lockfile from the root. <https://github.com/pnpm/pnpm/blob/main/pnpm11/deps/compliance/commands/src/audit/audit.ts>
- Noise: reports per advisory with all dependency _paths_ (capped, `pnpm why`), so counts are lower than Dependabot's per-version fan-out; `--prod` at the root still includes production deps of _all_ workspaces (client, docs), not just the image. For the image's tree run it inside the `pnpm deploy` output dir (`./prod/main`) or scan the image with Trivy/osv-scanner instead.
- Advisory-first: `pnpm audit --prod --audit-level high --json > pnpm-audit.json` with `continue-on-error: true`, upload the JSON as artifact and print the table in the job summary. Blocking: drop `continue-on-error`. No SARIF output (not documented).
- Related supply-chain setting: `minimumReleaseAge` (install cooldown) — `--fix` adds patched versions to `minimumReleaseAgeExclude`. <https://pnpm.io/cli/audit>

**C3. osv-scanner (Google, Apache-2.0)**

- Scans `pnpm-lock.yaml` (listed under JavaScript with `package-lock.json`, `yarn.lock`, `bun.lock`) and container images (`scan image name:tag` pulls via `docker` if not local; `--archive` for a tar; attributes findings to layers and to the base image). Output formats: table, markdown, vertical, HTML, JSON, **SARIF**, SPDX, CycloneDX. Exit codes: 0 no findings, 1 findings, 127 general error, 128 no packages found. **No severity-threshold flag is documented.** <https://github.com/google/osv-scanner/blob/main/docs/supported_languages_and_lockfiles.md>, <https://github.com/google/osv-scanner/blob/main/docs/scan-image.md>, <https://github.com/google/osv-scanner/blob/main/docs/output.md>
- Suppression: `osv-scanner.toml` per directory (or `--config` for all) with `[[IgnoredVulns]] id/ignoreUntil/reason` and `[[PackageOverrides]]` (`group = "dev"` + `ignore = true` drops dev-only deps; `effectiveUntil`). <https://google.github.io/osv-scanner/configuration/>
- GitHub Action: reusable workflows `google/osv-scanner-action/.github/workflows/osv-scanner-reusable.yml` (push/schedule) and `osv-scanner-reusable-pr.yml` (fails only on vulnerabilities _new_ in the PR). Inputs: `scan-args` (default `--recursive ./`), `results-file-name` (`results.sarif`), `upload-sarif` (true), **`fail-on-vuln` (default true → set `false` for advisory)**, `matrix-property`. Permissions: `security-events: write`, `actions: read`, `contents: read`. <https://google.github.io/osv-scanner/github-action/>
- Blocking on High only: not natively; either accept "any vuln" blocking in PR-diff mode (only _new_ findings, so low noise), or gate via the ruleset `code_scanning` rule with `security_alerts_threshold: high_or_higher` on the uploaded SARIF (requires `security-severity` in the SARIF — verify on first upload).

**C4. `actions/dependency-review-action` (GitHub, PR-only)**

- Diffs the dependency graph between base and head; inputs: `fail-on-severity` (default `low`; `critical|high|moderate|low`), `fail-on-scopes` (default `runtime`), `allow-licenses`/`deny-licenses` (SPDX), `deny-packages`, `allow-ghsas`, `comment-summary-in-pr` (default `never`; needs `pull-requests: write`), **`warn-only` (default false; true = log everything as warnings)**, `show-openssf-scorecard` (true). Requires dependency graph and `on: pull_request`. <https://github.com/actions/dependency-review-action>, <https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/configuring-the-dependency-review-action>
- Advisory: `warn-only: true`, `comment-summary-in-pr: on-failure`. Blocking: `warn-only: false`, `fail-on-severity: high`, and require the check in the ruleset. pnpm: covered because dependency graph reads `pnpm-lock.yaml`; no pnpm-specific caveat is documented. <https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/dependency-graph-supported-package-ecosystems>

### D. Secret scanning

**D1. GitHub secret scanning + push protection (free; push protection currently off)**

- Push protection "blocks pushes that contain secrets before they reach your repository" (CLI pushes, web commits, uploads, REST). Bypass reasons: "It's used in tests" / "It's a false positive" (alert created and closed) / "I'll fix it later" (open alert); every bypass is audit-logged and e-mailed to owners/security managers/admins. Delegated bypass (approval workflow) is paid. <https://docs.github.com/en/code-security/concepts/secret-security/push-protection>, <https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection>
- Noise: push protection "only supports the most recent token versions that secret scanning can identify with confidence"; generic (non-provider) patterns cover private keys and connection strings — plan availability for public repos not confirmed, the toggle exists and is off here. <https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns>
- Setting names (REST `PATCH /repos/{o}/{r}` → `security_and_analysis`): `secret_scanning_push_protection`, `secret_scanning_non_provider_patterns`, `secret_scanning_ai_detection`. Results: Security → Secret scanning; REST `GET /repos/{o}/{r}/secret-scanning/alerts`. <https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28>

**D2. gitleaks (MIT CLI; the GitHub Action is not MIT)**

- CLI: `gitleaks git` (history via `git log -p`), `gitleaks dir`, `gitleaks stdin`; `--report-format json|csv|junit|sarif|template`, `--report-path`, `--redact`, `--baseline-path` (ignore previously accepted findings), `--exit-code` (override the default 1-on-leak), `--log-opts` (limit to a commit range), `--config` with `[extend] useDefault = true`, `[[allowlists]]` (paths, regexes, stopwords, commits), inline `gitleaks:allow`, `.gitleaksignore` fingerprints. Exit: 0 clean, 1 leaks or error, 126 unknown flag. <https://github.com/gitleaks/gitleaks>
- `gitleaks/gitleaks-action` v2: "the license has changed from MIT to a license" and `GITLEAKS_LICENSE` is "required for organizations, not required for user accounts" (free key via a Google form). open-dpp is an organisation → either obtain the key or run the CLI/Docker image directly (recommended: no third-party licence dependency). <https://github.com/gitleaks/gitleaks-action>
- Advisory: `gitleaks git --redact --exit-code 0 --report-format sarif --report-path gitleaks.sarif` then `upload-sarif` with `category: gitleaks`. Blocking: `--exit-code 1` (default) and make the check required. Expected noise: test fixtures and example `.env` files (the repo commits `.env.dev.example` and test env values in workflows) → allowlist by path in `.gitleaks.toml` with `useDefault = true`.

### E. Container scanning (ghcr.io images, Dockerfile)

**E1. Trivy (Aqua, Apache-2.0)**

- Detects OS packages (Debian base of `node:25-slim`), language packages (`pnpm-lock.yaml` for fs scans — dev deps excluded by default, `--include-dev-deps` to add them, `Dev` field honoured for lockfile v9+; in images, `node_modules/*/package.json`), secrets (`scanners: vuln,secret` is the action default), misconfigurations for `Dockerfile`/`Containerfile` (Docker Compose is **not** an IaC type), licences. <https://trivy.dev/latest/docs/coverage/language/nodejs/>, <https://trivy.dev/latest/docs/coverage/iac/>
- Image targets: by `image@sha256:…` digest, `--platform linux/arm64` for the second manifest (default `linux/amd64`), auth via `TRIVY_USERNAME`/`TRIVY_PASSWORD` or `trivy registry login` (the workflow already runs `docker/login-action` to ghcr.io). <https://trivy.dev/latest/docs/target/container_image/>
- Filtering: `--severity HIGH,CRITICAL`; `--ignore-unfixed` (= `--ignore-status affected,will_not_fix,fix_deferred,end_of_life`) — essential for Debian base images where many CVEs have no fix; `.trivyignore` (`CVE-… exp:YYYY-MM-DD`) or `.trivyignore.yaml` (per-finding `paths`, `purls`, `expired_at`, `statement`; pass with `--ignorefile`); Rego `--ignore-policy`; VEX `--vex`; `--show-suppressed`. <https://trivy.dev/latest/docs/configuration/filtering/>
- Action `aquasecurity/trivy-action`: `scan-type` (`image`|`fs`|`config`|…), `image-ref`, `format` (`table|json|sarif|cyclonedx|spdx-json|github|…`), **`exit-code` (default `0` = advisory)**, `severity` (default all five), `ignore-unfixed`, `scanners`, `trivyignores`, `trivy-config`, `limit-severities-for-sarif` (SARIF otherwise contains all severities regardless of `severity`), built-in DB cache. DB pulls fall back through `mirror.gcr.io/aquasec` then `ghcr.io/aquasecurity` (429/5xx trigger the next mirror; `--db-repository` takes multiple values). <https://github.com/aquasecurity/trivy-action>, <https://trivy.dev/latest/docs/configuration/db/>
- Advisory: `exit-code: 0`, `format: sarif`, `upload-sarif` with `if: always()` and `category: trivy-image-<platform>`. Blocking: `exit-code: 1`, `severity: HIGH,CRITICAL`, `ignore-unfixed: true`, and/or the ruleset `code_scanning` rule for tool "Trivy".

**E2. Grype + Syft (Anchore, Apache-2.0)**

- Grype scans images (`registry:`, `docker:`, `docker-archive:`, `oci-archive:`), directories and SBOMs (`sbom:`; `syft <image> -o json | grype`); `--fail-on negligible|low|medium|high|critical`, `--only-fixed`, `-o table|json|sarif|cyclonedx-json|…`; `.grype.yaml` `ignore:` rules (vulnerability, fix-state, vex-status, package name/version/type/location) — ignored matches stay visible as `ignoredMatches` in JSON. <https://github.com/anchore/grype>
- Action `anchore/scan-action`: **`fail-build` default `true`** and `severity-cutoff` default `medium` — both must be changed for advisory (`fail-build: false`), then `severity-cutoff: high`, `only-fixed: true` for blocking; `output-format: sarif` → `upload-sarif`. <https://github.com/anchore/scan-action>
- Value: scanning the _same_ syft SBOM for source and image gives one evidence chain (SBOM → vulns); running both Trivy and Grype doubles noise, so pick Trivy as the gate and keep Grype as a Review-Run cross-check.

### F. SBOM

- **`@cyclonedx/cyclonedx-npm`**: "utilizes npm to collect evidences of installed packages" (needs `npm >= 9`, uses the npm executable); no pnpm support is mentioned anywhere → not usable for a pnpm workspace without an npm install tree. <https://github.com/CycloneDX/cyclonedx-node-npm>
- **cdxgen** (`@cdxgen/cdxgen`, Apache-2.0): Node.js project types include `pnpm`, reads `pnpm-lock.yaml`, runnable via `pnpm dlx @cdxgen/cdxgen -o bom.json .`; richer (evidence, BOM audit) but a heavier dependency than syft. <https://github.com/CycloneDX/cdxgen/blob/main/docs/PROJECT_TYPES.md>, <https://github.com/CycloneDX/cdxgen>
- **Syft**: `javascript-lock-cataloger` parses `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`; `javascript-package-cataloger` parses `package.json` (covers `node_modules` inside the image). Formats: CycloneDX (JSON/XML), SPDX (JSON/tag-value), syft-json. <https://oss.anchore.com/docs/capabilities/all-packages/>, <https://github.com/anchore/syft>
- **`anchore/sbom-action`**: inputs `path`/`file`/`image` (mutually exclusive), `format` (default `spdx-json`; `cyclonedx-json` available), `output-file`, `artifact-name`, `upload-artifact` (true), **`upload-release-assets` (true — "automatically upload all SBOMs as release assets" when run on a release event; needs `contents: write`)**, `dependency-snapshot` (submit to the dependency graph), `registry-username/password` for private images. <https://github.com/anchore/sbom-action>
- Monorepo gotcha: one SBOM of the repo root describes _all_ workspaces (client, docs, e2e); the deliverable SBOM for the product is the **image** SBOM (production tree of `apps/main` + client bundle) — generate both, label them, attest the image one.

### G. Provenance & attestations

- **GitHub artifact attestations**: "Artifact attestations work in public repositories across all GitHub plans"; public repos sign with the **Sigstore Public Good** instance and land in its public transparency log; SLSA v1.0 Build L2 (L3 with a reusable workflow). Actions: `actions/attest` (v4; `attest-build-provenance` and `attest-sbom` are now wrappers over it). Container inputs: `subject-name` = fully-qualified image name without tag, `subject-digest` = `sha256:…`, `push-to-registry: true` stores the attestation as an OCI referrer (requires prior `docker/login-action`); `sbom-path` accepts SPDX/CycloneDX (≤16 MB) for an SBOM attestation. Permissions: `id-token: write`, `attestations: write`, `contents: read`, `packages: write`. Verify: `gh attestation verify oci://ghcr.io/open-dpp/open-dpp:TAG -R open-dpp/open-dpp`; view under the repo's Actions → Attestations. <https://docs.github.com/en/actions/concepts/security/artifact-attestations>, <https://github.com/actions/attest>, <https://github.com/actions/attest-build-provenance>, <https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations>
- **BuildKit already does part of this**: for **public repositories** `docker/build-push-action` "automatically" adds provenance attestations with `mode=max` (private: `mode=min`) when pushing through the docker-container driver; `sbom: true` adds a BuildKit SBOM attestation; none is added with `load: true`. `mode=max` embeds source and build args — fine here (only `APP_VERSION`), but keep secrets out of `build-args`. Whether the attestations survive the `docker buildx imagetools create` manifest merge in `build.yml` is not confirmed → check with `imagetools inspect`. <https://docs.docker.com/build/ci/github-actions/attestations/>
- **cosign** (Sigstore, Apache-2.0): keyless signing binds the GitHub OIDC identity to an ephemeral key via Fulcio and logs to Rekor; in Actions it needs `id-token: write` and `sigstore/cosign-installer`; verification requires `--certificate-identity(-regexp)` and `--certificate-oidc-issuer` (`https://token.actions.githubusercontent.com` for Actions); `cosign verify-attestation --type` for SBOM/provenance predicates; signatures are checked against the image digest. Use only if a consumer needs `cosign verify` instead of `gh attestation verify` — both sit on the same Public Good log. <https://docs.sigstore.dev/cosign/signing/overview/>, <https://docs.sigstore.dev/cosign/verifying/verify/>, <https://github.com/sigstore/cosign-installer>
- Where to attest in `build.yml`: after the `merge` job creates the manifest list — attest the **index digest** (what `docker-compose.yml` pulls), optionally also the per-platform digests.

### H. DAST — OWASP ZAP baseline against the compose stack

- `zap-baseline.py` "runs the ZAP spider against the specified target for (by default) 1 minute and then waits for the passive scanning to complete" — no active attacks. Options: `-m mins`, `-a` (alpha passive rules), `-j` (AJAX spider, for the Vue SPA), `-c config_file` (rule id TAB `WARN|FAIL|IGNORE`, optional `OUTOFSCOPE` regex), `-I` (do not fail on WARN), `-n context_file` + `-U user` for authenticated scans, `-z` raw ZAP options. Exit: 0 pass, 1 ≥1 FAIL, 2 WARN only, 3 other failure. <https://www.zaproxy.org/docs/docker/baseline-scan/>
- Action `zaproxy/action-baseline`: inputs `target`, `rules_file_name`, `docker_name` (default `ghcr.io/zaproxy/zaproxy:stable`), `cmd_options`, `issue_title`, `token`, **`fail_action` (default `false` = advisory)**, `allow_issue_writing` (default `true` — opens/updates a GitHub issue "ZAP Scan Baseline Report" → set `false` on a public repo to keep findings private), `artifact_name` (default `zap_scan` with `report_html.html`, `report_md.md`, `report_json.json`). It runs `docker run -v $GITHUB_WORKSPACE:/zap/wrk/:rw --network="host" … zap-baseline.py -t <target> -J … -w … -r …`, so a compose stack publishing `3000` on the runner is reachable as `http://localhost:3000` (the `e2e.yml` job already stands the stack up). <https://github.com/zaproxy/action-baseline/blob/master/action.yml>, <https://github.com/zaproxy/action-baseline/blob/master/index.js>
- Noise: passive rules (missing headers, cookie flags, CSP, cache-control, version disclosure) fire on every page → start with a generated rules file (`-g`), keep WARN, promote header rules to FAIL after the baseline. Blocking: `fail_action: true` and a rules file with `FAIL` lines (WARN alone = exit 2 → still fails unless `-I`).
- API: `zap-api-scan.py -t <openapi> -f openapi` "imports the definition … and then runs an Active Scan" tuned to APIs; `-S` safe mode falls back to baseline. NestJS exposes Swagger (`api-docs.json` is gitignored → generate it in the job). <https://www.zaproxy.org/docs/docker/api-scan/>

### I. OpenSSF Scorecard

- "The Scorecards GitHub Action is free for all public repositories." Triggers: `push`, `schedule` (default branch only); `pull_request`/`workflow_dispatch` experimental. Inputs: `results_file`, `results_format` (`sarif|json`), `publish_results` (badge + REST API at `api.scorecard.dev`; needs `id-token: write`), `repo_token`. Results: SARIF via `github/codeql-action/upload-sarif` → Security tab; artifact readable by anyone for 5 days; badge. Rulesets (not classic branch protection) are readable with the default `GITHUB_TOKEN`. <https://github.com/ossf/scorecard-action>
- Constraints when publishing: no workflow-level `env`/`defaults`, no workflow-level write permissions, `id-token: write` only on the Scorecard job, Ubuntu runner, and the job may only use `actions/checkout`, `actions/upload-artifact`, `github/codeql-action/upload-sarif`, `ossf/scorecard-action`, `step-security/harden-runner`. Scorecard never fails the build on score; it is inherently advisory — Controls read the per-check score (`Pinned-Dependencies`, `Token-Permissions`, `Branch-Protection`, `Dangerous-Workflow`, `SAST`, `Vulnerabilities`, `Security-Policy`, `Dependency-Update-Tool`, `Signed-Releases`, `Code-Review`, `Maintained`, ...).

### J. Action pinning and runner hardening

- **Policy switch (GitHub, 2025-08-15)**: repository/organisation Actions setting "Require actions to be pinned to a full-length commit SHA" — "any workflow that attempts to use an action that isn't pinned will fail"; reusable workflows may still be referenced by tag. This is the _blocking_ form; enable it only after every workflow is pinned. <https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/>, <https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository>
- **pinact** (MIT): `pinact run` rewrites `uses:` to full SHAs with `# vX.Y.Z` comments; `--check` exits 1 when anything is unpinned (2 when it cannot fix, 3 on API errors); `--verify` checks that the comment's version really resolves to the SHA; `--update` bumps; `--min-age` applies a release-age cooldown; config `.pinact.yaml`/`.github/pinact.yaml` (ignored actions, file globs); needs `GITHUB_TOKEN` for rate limits; `suzuki-shunsuke/pinact-action` wraps it for CI. Advisory: `pinact run --check` with `continue-on-error`; blocking: remove it, then flip the policy switch. <https://github.com/suzuki-shunsuke/pinact>
- **StepSecurity secure-repo** (AGPL-3.0 web app, `app.stepsecurity.io/securerepo`, "no need to install any App or grant write access" for public repos): generates one PR that pins actions to SHAs, pins Dockerfile images to digests, sets least-privilege `permissions`, adds harden-runner, Dependabot, CodeQL, dependency review and Scorecard workflows. Useful as a one-off generator; review the PR rather than trusting it. <https://github.com/step-security/secure-repo>
- **harden-runner** (Apache-2.0; "free for public repositories on GitHub-hosted runners", enterprise for private/self-hosted): first step of each job; `egress-policy: audit` records every outbound endpoint and shows it in the job summary and `app.stepsecurity.io`; `block` + `allowed-endpoints` terminates on unlisted egress (protects against exfiltration from compromised actions); `disable-sudo`, `disable-file-monitoring`. Advisory = `audit`; blocking = `block` after the audit log shows the endpoint set. <https://github.com/step-security/harden-runner>

### K. Rulesets — the mechanism behind "flip to blocking"

- The current `protect-main` ruleset has no `required_status_checks` and no `code_scanning` rule. Blocking is added with `required_status_checks.required_status_checks[].context` (the job/check name) plus `strict_required_status_checks_policy`, and with `code_scanning.code_scanning_tools[]` (`tool`, `alerts_threshold`, `security_alerts_threshold`). Rule types come from the REST rules API; the UI path is Settings → Rules → the ruleset → "Require status checks to pass" / "Require code scanning results". <https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28>, <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets>
- Consequence for #791: advisory mode needs no ruleset change at all; the "flip" is one ruleset edit per tool plus the per-tool exit-code/`fail-*` inputs listed above.

Reading pattern for a Review Run: every SARIF producer lands in **one** place (Security → Code scanning, queryable per `tool_name`), Dependabot and secret scanning have their own REST endpoints, ZAP and pnpm-audit are **artifacts** of the run, SBOM/provenance are **release assets + registry attestations**, Scorecard is a **public JSON API**. A small evidence-collection script (candidate for the run procedure, #781) can therefore snapshot the entire automated evidence set with `gh api` + `gh run download` + `gh attestation verify` and file it in the private run folder.

Status-free register note: the register lists _which tool verifies_ and _where evidence lives_; whether a tool currently blocks is workflow/ruleset state, not register content.
