# Research: Which TÜViT scheme applies to open-dpp, and what does it test against?

- Ticket: [#773](https://github.com/open-dpp/open-dpp/issues/773) (part of map [#772](https://github.com/open-dpp/open-dpp/issues/772))
- Date of research: 2026-09-03
- Sources: primary only — tuvit.de, bsi.bund.de PDFs (text-extracted), the official OWASP ASVS 5.0.0 repository tag, and the CRA as published on EUR-Lex. One TÜViT-issued certificate PDF (hosted by its holder) is used as a primary artifact. The single secondary source (a certificate holder's blog post) is marked as such.

## Question

TÜV Informationstechnik GmbH (TÜViT, TÜV NORD GROUP) runs several distinct schemes — ISO 27001 / IT-Grundschutz, Common Criteria, Trusted Site / Trusted Product seals, web-application penetration tests, CRA conformity assessment. Which is the realistic target for a web application + SaaS like open-dpp, what standard(s) does that scheme test against, what evidence does an assessor expect, what does it require **beyond OWASP ASVS 5.0 Level 2**, and does TÜViT publish a test catalogue we can align the Control Register to?

## Short answer

1. **The realistic target is TÜViT's "Security Qualification (SQ)"**, marketed as **Trusted Site Security (TSS)** for IT systems and **Trusted Product Security (TPS)** for IT products. TÜViT states the scope runs "from simple software components to appliance solutions or web applications through to distributed systems"; certificates have been issued for web portals (a remote-service portal at SEAL-3 in 2024; an e-procurement platform at SEAL-4 in 2025). Common Criteria, BSZ and EUCC are not realistic for a web app (BSZ scopes are hardware-only; CC is heavyweight). ISO 27001 / IT-Grundschutz and BSI C5 are *organisational / operator* schemes that complement, not replace, a product/system certificate — they are the Ring 4 / Ring 3 backdrop, and ISO 27001 is also the basis of CRA Module H.
2. **What SQ tests against:** not a fixed public standard. The scheme has seven criteria groups gated by five **Security Assurance Levels (SEAL-1…5)**: Technical Security Requirements (SEAL-1+), Vulnerability Assessment & Penetration Testing (SEAL-2+), Architecture & Design and Development Process (SEAL-3+), Operating Instructions and Source Code Analysis (SEAL-4+), Change Management (SEAL-5). A certificate requires **at least SEAL-3** and is valid **2 years**. The technical security requirements are **product-specific**, agreed in a kick-off workshop, must be specified per ISO/IEC 17007 and must be derived from a threat/risk analysis, a protection profile, or "published security requirements of recognized authorities or bodies of IT security" — which is exactly the slot an ASVS 5.0 L2 Control Register fills. The test itself is a penetration test plus vulnerability analysis; TÜViT's own web-pentest methodology cites OWASP ASVS, WSTG, Top 10 and the BSI penetration-test concept.
3. **Beyond ASVS L2** the SQ adds, at SEAL-3: a documented, verifiable requirements specification; an architecture/design review ("must not contain any conceptual vulnerability"); a defined development lifecycle with security testing and vulnerability elimination in maintenance; a risk analysis of pentest results. SEAL-4 adds reviewed operating/installation/admin documentation and source-code analysis; SEAL-5 adds documented patch/change management. None of these are ASVS requirements — ASVS 5.0 explicitly "does not prescribe development lifecycle activities". The CRA (Annex I Part II, Art. 13/14) and BSI TR-03185/TR-03183 supply the concrete process controls (SBOM, CVD policy, reporting, support period) that fill that gap.
4. **Evidence an assessor expects:** the technical security requirements document; threat and risk analysis; architecture/design documentation; development-process description incl. security tests; operating/installation/administration manuals; test accounts and (for grey/white box) API docs, communication matrix and source code; dependency inventory/SBOM; vulnerability-handling and change-management procedures. Results are recorded so a third party can repeat them (BSI TR-03161-2 ch. 4 is the public model for this).
5. **Published catalogue?** **No.** The "Trusted Site Security / Trusted Product Security, Security Qualification (SQ) Requirements Catalog for Version 10.0" (doc. version 2.9, 2022-11-11) is referenced on certificates but is not downloadable; TÜViT's SQ whitepaper is form-gated and the older service-description PDFs are gone from tuvit.de. The SQ certification programme itself is described as the certification body's **non-accredited area**. The public catalogues TÜViT does test web applications against are BSI's: **TR-03161 Part 2 (Web Applications)** — 11 objectives, ~210 requirement IDs, explicit audit depths and result recording, built on ASVS/WSTG — and **IT-Grundschutz APP.3.1 / CON.10**. These, plus TR-03185 (secure SDLC) and TR-03183-2 (SBOM), are what the Control Register should align to for the non-ASVS layer.

## Findings

### A. TÜViT's scheme landscape

1. TÜViT's "Norms, Standards & Guidelines" overview lists: ISO 27001, IT-Grundschutz, Common Criteria, BSI C5, Security Qualification (SQ), Trusted Site Privacy, IEC 62443, BSI TR-03161, ISO 27701, ISO 22301 and BSZ (Fixed-time Cybersecurity Certification). Source: https://www.tuvit.de/en/services/norms-standards-guidelines/
2. **SQ = TSS + TPS.** "TÜVIT has developed the Security Qualification (Sicherheitstechnische Qualifizierung, SQ) procedure for the testing and certification of complex IT systems and IT products", offered "as Trusted Site Security (TSS) for IT systems and Trusted Product Security (TPS) for IT products". "The range extends across all technologies from simple software components to appliance solutions or web applications through to distributed systems." Sources: https://www.tuvit.de/en/services/cyber-security/sq-best-practice-certification-procedure/ ; German: https://www.tuvit.de/de/leistungen/normen-standards-richtlinien/sicherheitstechnische-qualifizierung-sq/
3. **SQ procedure (TÜViT's own description):** (1) kick-off workshop defining the certification object and the technical security requirements, "approved by the certification body"; (2) "penetration tests and vulnerability analyses, depending on the selected Security Assurance Level (SEAL)"; (3) results "evaluated in a risk analysis and documented in a meaningful test report"; (4) certificate, optionally published on tuvit.de. Test criteria for IT products: technical security requirements, architecture and design, development process, installation and operation, operating specifications, vulnerability analyses and penetration tests, change management (IT systems: same minus development process and operating specifications). Source: https://www.tuvit.de/en/services/norms-standards-guidelines/security-qualification-sq/
4. TÜViT frames SQ as "Proof of the requirements/standards defined by the EU (CENELEC) for compliance with various laws such as NIS-2, CRA or RED", but the public page names no test standard (no ISO 27001, IT-Grundschutz, OWASP or BSI TR). The SEAL levels are not defined on the page; the whitepaper is behind a form. Source: same as 2.

### B. What an SQ certificate actually attests (primary artifact)

5. A TÜViT-issued **"Certificate Security — Trusted Product", ID 6148.24** (symmedia GmbH, "remote service portal software symmedia SP/1, Version 12", validity 2024-01-18 – 2026-01-18) confirms the product "fulfils all requirements of the criteria Security Qualification (SQ), Version 10.0, Security Assurance Level SEAL-3". Source (TÜViT document hosted by the certificate holder): https://www.sumitomo-shi-demag.eu/fileadmin/user_upload/Dokumente/Security_Assurance_Level_SEAL-3_EN.pdf
6. Its appendix names the **certification scheme**: "Zertifizierungsprogramm (nicht akkreditierter Bereich) der Zertifizierungsstelle der TÜV Informationstechnik GmbH", version 1.1, 2020-03-01 — i.e. SQ runs in the certification body's **non-accredited** area. Source: same.
7. It names the **evaluation requirements**: "Trusted Site Security / Trusted Product Security, Security Qualification (SQ) Requirements Catalog for Version 10.0, documentation version 2.9 as of 2022-11-11" plus "Product-specific security requirements". Neither document is available on tuvit.de (checked 2026-09-03; the former service descriptions `TUEViT_TS_TP_Security_V2_7.pdf` / `_V3_0.pdf` return 404 or redirect to the homepage). Source: same; https://www.tuvit.de/fileadmin/Content/TUV_IT/pdf/Dienstleistungsbeschreibungen/deutsch/TUEViT_TS_TP_Security_V3_0.pdf (404).
8. The **product-specific security requirements** on that certificate are five short, testable statements: Identification & Authentication (per user/system relation), Access Control ("A user must not be able to extend his access privilege with reasonable effort"), Encrypted communication channel/path, Data Flow Control ("only connections needed for operation are possible"), Logging ("Security-relevant events must be logged", with hash-chained log entries noted as a hardening). Source: same.
9. The **seven SQ criteria groups and their SEAL gating** (quoted from the certificate appendix):
   - "Technical Security Requirements (as of SEAL-1): The technical security requirements must be documented, consistent and verifiable. The specification must be made in accordance with ISO / IEC 17007. In addition, technical security requirements must be derived in the framework of an individual threat and risk analysis, they must be derived from previously defined protection profiles, or they must conform to published security requirements of recognized authorities or bodies of IT security."
   - "Architecture and Design (as of SEAL-3): … It must not contain any conceptual vulnerability that allows bypassing or disabling security-relevant components. The hardening and protection measures must be adequate and effective."
   - "Development Process (as of SEAL-3): Development of the IT product must follow a defined development life cycle taking into account at least the phases of planning, analysis, design, implementation, testing, deployment and maintenance. The maintenance phase … must consider and eliminate vulnerabilities … tests with respect to security functionality of the IT product must be considered."
   - "Operating Instructions (as of SEAL-4): The documentation consisting of security requirements for the operating environment of the product, manuals for installation and administration as well as manuals for the end user must be clearly understandable and comprehensible."
   - "Vulnerability Assessment and Penetration Testing (as of SEAL-2): The security measures of the IT product must withstand penetration testing. … The IT product must be configured securely, must meet all of the defined technical security requirements and must not have any exploitable vulnerability."
   - "Source Code Analysis (as of SEAL-4): The source code must not contain vulnerabilities, errors or inconsistencies, such as e. g. undocumented commands, parameters and test functions."
   - "Change Management (as of SEAL-5): Patch management must be completely documented and suitable for the IT product. … Amendments of the IT product must not lead to a reduction of the security level achieved."
   - "A certificate can be issued for IT products having successfully passed the evaluation and reaching an overall level of at least SEAL-3." Source: same.
10. **Web/SaaS precedents.** Besides the remote-service portal above (primary), the German e-procurement platform DTVP reported in March 2025 a TÜViT "Zertifikat Trusted Site Security / Trusted Product Security" at "SEAL-4-Niveau", with the audit covering "die Zugriffskontrolle, die Datensicherheit und Transportsicherheit, die Systemhärtung, die Validierung von Ein- und Ausgabedaten sowie der Schutz vor unbefugtem Zugriff und Datenmanipulation". *Secondary source (certificate holder's blog), not verified against a certificate PDF:* https://blog.cosinex.de/2025/03/27/dtvp-erhaelt-tuev-zertifizierung/ . TÜViT's own reference list additionally shows web platforms under Trusted Site Privacy and ISO 27001 (Deutsche Telekom billing systems incl. "tests on the web application"; Deutsche Post E-POST platform) — https://www.tuvit.de/en/about-us/references/

### C. TÜViT's penetration-test methodology (the engine inside SQ)

11. TÜViT's web-pentest page names its basis: the "OWASP Application Security Verification Standard (ASVS)" (as "basic security requirements for web applications"), the "OWASP Web Security Testing Guide (WSTG)" for verifying them, the "OWASP Top 10", and the "BSI Implementation Concept for penetration tests". Grey box ("with additional information, e.g. test access data and (API) documentation") is the standard; white box adds "architecture/design documents, communication matrix or source code". Test areas: access control/authorisation, input/output validation, authentication & session management, security misconfiguration, information disclosure, business logic, cryptography/TLS, data protection, port scans/TLS configuration. Source: https://www.tuvit.de/en/services/applications/web-pentest/
12. Report format: management summary; per-vulnerability risk level "informative, low, medium, high or critical"; vulnerability table and risk visualisation; proof-of-concept; measures; CVE references; technical attachments; optional re-test. CVSS is **not** named. TÜViT is "certified by the BSI as an IT security service provider for IS audits and penetration tests". Source: https://www.tuvit.de/en/services/auditing-evaluation/penetration-tests/
13. The BSI documents behind "recognised standards": the study *Durchführungskonzept für Penetrationstests* (five phases: Vorbereitung; Informationsbeschaffung und -auswertung; Bewertung der Informationen / Risikoanalyse; Aktive Eindringversuche; Abschlussanalyse; six classification criteria: Informationsbasis, Aggressivität, Umfang, Vorgehensweise, Technik, Ausgangspunkt) — https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Publikationen/Studien/Penetrationstest/penetrationstest.pdf — and *Ein Praxis-Leitfaden für IS-Penetrationstests* v1.2 (Nov 2016), which states "Das BSI empfiehlt, grundsätzlich Whitebox-Tests durchzuführen" and grades findings hoch/mittel/niedrig/zur Information with reaction deadlines — https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Sicherheitsberatung/Pentest_Webcheck/Leitfaden_Penetrationstest.pdf

### D. Schemes that are *not* the target, and why

14. **Common Criteria / EUCC:** TÜViT is an ITSEF, but CC targets are security products with a Security Target/Protection Profile; no web-app precedent on tuvit.de. Source: https://www.tuvit.de/en/services/norms-standards-guidelines/common-criteria/
15. **BSZ (Beschleunigte Sicherheitszertifizierung, EN 17640 FiT CEM):** BSI scheme, TÜViT as evaluation facility, 2-year certificate, CSPN-compatible — but the published BSI scopes are hardware/network products only (network components/embedded IP devices, telematics connectors, smart-meter-gateway HAN components). Sources: https://www.tuvit.de/en/services/norms-standards-guidelines/fixed-time-cybersecurity-certification-bsz/ ; https://www.bsi.bund.de/DE/Themen/Unternehmen-und-Organisationen/Standards-und-Zertifizierung/Zertifizierung-und-Anerkennung/Zertifizierung-von-Produkten/Beschleunigte-Sicherheitszertifizierung/beschleunigte-sicherheitszertifizierung_node.html
16. **ISO 27001 (org, Ring 4):** stage 1 documentation / stage 2 on-site, surveillance in years 1 and 2, re-certification after 3 years; evidence = ISMS scope, risk assessment and treatment, Statement of Applicability, policies. Source: https://www.tuvit.de/en/services/norms-standards-guidelines/iso-27001/
17. **BSI C5 (SaaS operator, Ring 3):** an **audit/attestation** (ISAE 3000), not a certification; 17 domains / 121 criteria; "includes all the criteria of ISO/IEC 27001 in the basic criteria". Domains directly relevant to open-dpp's operated instances: **PSS** (Product Safety and Security: PSS-02 identification of vulnerabilities via SAST/DAST/code review and third-party-library monitoring, PSS-03 online register of known vulnerabilities, PSS-04 error handling and logging, PSS-05…09 authentication/session/roles/authorisation, PSS-11 VM and container images), **DEV** (DEV-01…10: development policy, change risk assessment, testing, logging of changes, version control, production approvals, separation of environments), **OPS-10…17** logging and monitoring, **OPS-18…23** vulnerability/malfunction management incl. OPS-19 penetration tests. C5:2026 is final since March 2026 and ships machine-readable YAML. Sources: https://www.tuvit.de/en/services/norms-standards-guidelines/bsi-c5/ ; https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/CloudComputing/ComplianceControlsCatalogue/2020/C5_2020.pdf ; https://www.bsi.bund.de/DE/Themen/Unternehmen-und-Organisationen/Informationen-und-Empfehlungen/Empfehlungen-nach-Angriffszielen/Cloud-Computing/Kriterienkatalog-C5/C5_2025/C5_2025_node.html
18. **CRA conformity assessment via TÜViT:** TÜViT offers gap assessment ("risk management, vulnerability management, supply chain management, SBOM, documentation"), security-by-design checks, conformity assessment per Module A, B/C or H, a "Leak Detection Service" for Art. 14, and cyclic tests (pentest, code review, SAST, DAST). For Module H it requires "ein wirksames Informationssicherheitsmanagementsystem (ISMS) nach ISO/IEC 27001 … erweitert um die CRA-spezifischen Anforderungen der TR-03183-H". Status: "TÜV NORD wird diese Benennung beim BSI beantragen" — TÜViT is *not yet* a notified CRA body on its page. Sources: https://www.tuvit.de/en/topics/regulations/cyber-resilience-act/ ; https://www.tuvit.de/de/themen/regulierungen/cyber-resilience-act/ ; BSI as notifying authority and TR-03183-H as accreditation reference: https://www.bsi.bund.de/DE/Themen/Unternehmen-und-Organisationen/Informationen-und-Empfehlungen/Cyber_Resilience_Act/Notifizierung-CRA/notifizierung-cra.html

### E. Does the CRA even require third-party assessment for open-dpp?

19. A DPP web application appears in **no Annex III class** (Class I: identity management systems and PAM, browsers, password managers, anti-malware, VPN, network management, SIEM, boot managers, PKI, network interfaces, operating systems, routers/switches, security-relevant micro-processors/-controllers/ASICs, smart-home assistants and security products, connected toys, wearables; Class II: hypervisors/container runtimes, firewalls/IDS/IPS, tamper-resistant micro-processors/-controllers). A default product may use **Module A (internal control)**, Art. 32(1); FOSS manufacturers may use Module A even for Annex III products if the technical documentation is public, Art. 32(5). Source: https://eur-lex.europa.eu/eli/reg/2024/2847/oj/eng (Art. 32, Annex III)
20. **SaaS carve-out:** Recital 12 — "cloud services designed and developed outside the responsibility of a manufacturer of a product with digital elements do not fall within the scope of this Regulation. Directive (EU) 2022/2555 applies to cloud computing services and cloud service models, such as Software as a Service (SaaS)". A hosted backend is in scope only as "remote data processing" (Art. 3(2)) — "data processing at a distance for which the software is designed and developed by the manufacturer … and the absence of which would prevent the product with digital elements from performing one of its functions". Source: same (Rec. 11-12, Art. 3(2))
21. **Manufacturer vs steward:** Recital 15 lists monetisation triggers — "charging a price for technical support services where this does not serve only the recuperation of actual costs, by an intention to monetise, for instance by providing a software platform through which the manufacturer monetises other services" — which describes a FOSS project that also sells a hosted/whitelabel offering; Recital 18 keeps non-monetised FOSS out of scope. Steward obligations (Art. 24) are limited to a documented cybersecurity policy, cooperation with authorities and partial Art. 14 reporting. Source: same (Rec. 15, 18, 19; Art. 3(13), 3(14), 24)
22. **Essential requirements that go beyond ASVS:** Annex I Part I 2(b) secure-by-default incl. reset; 2(c) security updates, automatic by default with opt-out; 2(h) resilience incl. DoS; 2(j) limit attack surface; 2(l) "recording and monitoring relevant internal activity … with an opt-out mechanism for the user"; 2(m) secure permanent deletion and data transfer. Annex I Part II: SBOM "covering at the very least the top-level dependencies"; security updates separate from feature updates where feasible; "effective and regular security tests and reviews"; public disclosure of fixed vulnerabilities; CVD policy; reporting contact; secure update distribution; free security updates. Art. 13(8) support period ≥ 5 years; Art. 13(9) updates available ≥ 10 years; Art. 14: 24 h early warning / 72 h notification / 14-day final report for actively exploited vulnerabilities, **applicable from 11 September 2026** (Art. 71); Annex VII technical documentation (risk assessment, SBOM, CVD policy, test reports). Source: same
23. **Timeline:** entry into force 10 Dec 2024; Chapter IV (notification of CABs) from 11 June 2026; Art. 14 reporting from 11 Sept 2026; full application 11 Dec 2027. Source: same (Art. 71); mirrored by TÜViT: https://www.tuvit.de/en/topics/regulations/cyber-resilience-act/

### F. Public catalogues TÜViT tests web applications against (the alignable layer)

24. **BSI TR-03161 Part 2 "Web Applications" v2.0 (2024-09-11)** — TÜViT is a test body for it. Scope: "This TR is aimed at developers of web applications in the healthcare sector. In addition, it can be considered as a guideline for web applications that process or store sensitive data." Method: "It follows international standards, such as the Application Security Verification Standard [ASVS], and the Web Security Testing Guide [WSTG]" (referenced ASVS is **4.0**). Eleven objectives — (1) Intended use, (2) Architecture, (3) Source code, (4) Third-party software, (5) Cryptographic implementation, (6) Authentication, (7) Data security, (8) Paid resources, (9) Network communication, (10) Platform-specific interactions, (11) Resilience — with ~210 requirement IDs (O.Purp_n, O.Arch_n, O.Source_n, O.TrdP_n, O.Cryp_n, O.Auth_n, O.Pass_n, O.Data_n, O.Paid_n, O.Ntwk_n, O.Plat_n, O.Resi_n). Sources: https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/Publications/TechGuidelines/TR03161/TR-03161-2.pdf?__blob=publicationFile&v=2 ; TÜViT page: https://www.tuvit.de/en/services/norms-standards-guidelines/bsi-tr-03161/ ; BSI node: https://www.bsi.bund.de/EN/Themen/Unternehmen-und-Organisationen/Standards-und-Zertifizierung/Technische-Richtlinien/TR-nach-Thema-sortiert/tr03161/tr03161_node.html
25. TR-03161-2 chapter 4 is the only **public German description of how such an audit is run and recorded**: two audit depths — CHECK ("plausibility check" of the manufacturer's described measure, "analogue to the use of terms in Common Criteria Evaluation Methodology") and EXAMINE ("comprehensive source code analysis of the relevant implementation parts and penetration testing … always requires an independent assessment by the evaluator"); results PASS / INCONCLUSIVE / FAIL / NOT APPLICABLE; "The audit results must be recorded in a way that enables uninvolved third parties to repeat the audit steps based on the information in the report and achieve the same result … the tools used are visible in the report"; the manufacturer supplies "supporting statements in which he outlines the relevant implementation and provides a reference to the respective implementation". Chapter 5 requires a documented risk method (BSI 200-3, ISO 27005 or CEM Annex B) with data criticality classes very high / high / normal. Source: same PDF, ch. 4-5.
26. TR-03161-2 requirements with no ASVS counterpart (verbatim): O.Arch_1 "Security MUST be an integral part of the software development and life cycle for the entire web application and backend system."; O.Arch_7 "The manufacturer MUST provide the user with a low-barrier way to report security issues."; O.TrdP_1 "The provider MUST maintain a centralized and complete list of dependencies on third-party software."; O.TrdP_3 "Third-party software MUST be regularly checked for vulnerabilities by the developer … For all publicly known vulnerabilities, the manufacturer MUST analyze the extent to which the vulnerability affects the security of the overall system."; O.TrdP_4 "The manufacturer MUST submit a security concept that defines the tolerated continued use for the web application or the backend system based on the criticality of exploitable vulnerabilities. After the grace period has expired, the web application MUST NOT be offered for use."; O.TrdP_8 "Third party software that is no longer maintained, MUST NOT be used."; O.Source_8 "Tools for static code analysis SHOULD be used"; O.Data_1 "The factory setting of the web application MUST provide maximum security." Source: same PDF, ch. 3.
27. **BSI IT-Grundschutz (Edition 2023)** building blocks a German assessor maps a web app / SaaS to: APP.3.1 Webanwendungen und Webservices (Basis A1 Authentisierung, A4 Kontrolliertes Einbinden von Dateien und Inhalten, A7 Schutz vor unerlaubter automatisierter Nutzung, A14 Schutz vertraulicher Daten; Standard A8 Systemarchitektur, A11 Sichere Anbindung von Hintergrundsystemen, A12 Sichere Konfiguration, A21 Sichere HTTP-Konfiguration, **A22 Penetrationstest und Revision**; Erhöht A20 WAF), CON.10 Entwicklung von Webanwendungen (A1-A18 incl. A12 Verifikation essenzieller Änderungen, A16 Mehr-Faktor-Authentisierung, A17 Verhinderung der Blockade von Ressourcen), CON.8 Software-Entwicklung, SYS.1.6 Containerisierung (A6 Verwendung sicherer Images, A7 Persistenz von Protokollierungsdaten, A8 Sichere Speicherung von Zugangsdaten, A14 Aktualisierung von Images, A15 Limitierung der Ressourcen, A17 Ausführung ohne Privilegien, A23 Unveränderlichkeit), OPS.1.1.5 Protokollierung (A1 Sicherheitsrichtlinie, A4 Zeitsynchronisation, A6 zentrale Protokollierungsinfrastruktur, A10 Zugriffsschutz), OPS.1.1.3 Patch- und Änderungsmanagement, ORP.4, DER.1, DER.2.1. Sources: https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Grundschutz/IT-GS-Kompendium_Einzel_PDFs_2023/06_APP_Anwendungen/APP_3_1_Webanwendungen_und_Webservices_Edition_2023.pdf ; https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Grundschutz/IT-GS-Kompendium_Einzel_PDFs_2023/03_CON_Konzepte_und_Vorgehensweisen/CON_10_Entwicklung_von_Webanwendungen_Edition_2023.pdf ; https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Grundschutz/IT-GS-Kompendium_Einzel_PDFs_2023/07_SYS_IT_Systeme/SYS_1_6_Containerisierung_Edition_2023.pdf ; https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Grundschutz/IT-GS-Kompendium_Einzel_PDFs_2023/04_OPS_Betrieb/OPS_1_1_5_Protokollierung_Edition_2023.pdf
28. **BSI TR-03185 "Sicherer Software-Lebenszyklus"** Part 1 v1.0 (2024-08-06), derived from IT-Grundschutz plus IEC 62443-4-1, GSMA NESAS and NIST SP 800-218; Part 2 for open-source projects (2025-11-03, "regardless of team size, commercial or nonprofit background"; certification "derzeit nicht angeboten" for Part 2). Requirement examples: PROD.DEV.C.1 "In der Entwurfsphase der Software-Entwicklung MUSS eine Bedrohungsmodellierung durchgeführt werden" (C.2 lists mandatory content: data flows of sensitive data, trust boundaries, external components, debug interfaces, CVSS severity, mitigations); PROD.DEV.L.2 provenance of components "z.B. als SBOM" (→ TR-03183); PROD.FIX.A.3 "Es MUSS eine Meldestelle für informationssicherheitsbezogene Probleme des Produktes existieren und kommuniziert werden"; A.4 proactive monitoring of third-party vulnerabilities. ## Implications for the Control Register

Adoptable Controls **beyond ASVS 5.0 L2**, phrased as requirements. Status-free; the Ring is a proposal; IDs are provisional. Each Control names the source whose assessor would ask for it.

### Technical security requirements as an artefact (SQ criterion 1, SEAL-1; TR-03161-2 ch. 4)

- **TUV-REQ-01** — The Control Register MUST be a documented, internally consistent and verifiable specification of open-dpp's technical security requirements, structured so that each Control has one testable statement, a verification method and a pointer to the implementation (ISO/IEC 17007 style). *SQ criterion 1.*
- **TUV-REQ-02** — Each Control MUST be traceable to at least one of: the threat model, a published requirement set (ASVS 5.0, TR-03161-2, IT-Grundschutz APP.3.1/CON.10, CRA Annex I). *SQ criterion 1 ("derived from … threat and risk analysis … or … published security requirements of recognized authorities").*
- **TUV-REQ-03** — Every Review Run MUST record, per Control, an audit depth (CHECK or EXAMINE) and a result from {PASS, INCONCLUSIVE, FAIL, N/A}, plus the tools and steps used, such that an uninvolved third party can repeat the step. *TR-03161-2 ch. 4.1-4.2.*
- **TUV-REQ-04** — Each Review Run MUST include a documented risk analysis of Findings using a named method (CVSS v4.0 per the map, mapped to BSI 200-3 / ISO 27005 classes very high / high / normal for data criticality). *SQ step 3; TR-03161-2 ch. 5.*

### Architecture and design (SQ criterion 2, SEAL-3)

- **TUV-ARCH-01** — A maintained threat model MUST exist covering data flows of sensitive data, trust boundaries (tenant/organisation boundary, service tokens, MinIO, ClamAV, LLM egress), external components, debug/dev interfaces, and mitigations, with severity per CVSS. *TR-03185 PROD.DEV.C.1/C.2; SQ criterion 2.*
- **TUV-ARCH-02** — Architecture documentation MUST show that no security-relevant component (AuthGuard, PolicyGuard, MembersService ownership checks, upload scanning) can be bypassed or disabled by a conceptual path; the Review Run MUST include an architecture review step, not only tests. *SQ criterion 2 ("must not contain any conceptual vulnerability").*
- **TUV-ARCH-03** — The reference deployment MUST enforce data-flow control: only the network connections required for operation are permitted between containers and to the internet (egress allow-list incl. Mistral endpoint). *SQ product-specific requirement 4 (Data Flow Control); IT-Grundschutz SYS.1.6.A5.*

### Development process (SQ criterion 3, SEAL-3; CRA Annex I Part II; TR-03185)

- **TUV-DEV-01** — A written secure development lifecycle MUST exist naming the phases planning, analysis, design, implementation, testing, deployment, maintenance, and where security tests (unit/integration authz tests, SAST, dependency audit, ZAP baseline) run in CI. *SQ criterion 3; C5 DEV-01.*
- **TUV-DEV-02** — A machine-readable SBOM (CycloneDX ≥ 1.6 or SPDX ≥ 3.0.1, JSON) MUST be generated per release for both apps and the Docker images, with per-component creator, name, version, dependencies (completeness flagged), licences and SHA-512 of the deployable. *CRA Annex I Part II(1); TR-03183-2 v2.1.0; TR-03161-2 O.TrdP_1; extends ASVS 15.1.2.*
- **TUV-DEV-03** — Third-party components MUST be monitored for published vulnerabilities continuously; for each affecting CVE the impact on the overall system MUST be analysed and recorded; unmaintained components MUST NOT be used. *TR-03161-2 O.TrdP_3/O.TrdP_8; CRA Art. 13(5)-(6); C5 PSS-02.*
- **TUV-DEV-04** — A vulnerability-tolerance concept MUST define, per severity, the maximum time a known exploitable vulnerability may remain in a released version (the map's SLAs Critical ≤ 7 d · High ≤ 30 d · Medium ≤ 90 d), and what happens when it lapses. *TR-03161-2 O.TrdP_4; ASVS 15.1.1 covers only the documented timeframe, not the consequence.*
- **TUV-DEV-05** — Security fixes MUST be releasable separately from feature changes (patch releases on the supported line). *CRA Annex I Part II(2).*
- **TUV-DEV-06** — Dependencies and transitive dependencies MUST be resolved only from the expected registry (lockfile integrity, pinned registry, provenance checks) — adopt ASVS L3 15.2.4. *SQ criterion 3 maintenance; CRA Annex I Part II.*
- **TUV-DEV-07** — Static code analysis and secret scanning MUST run on every change, and the build MUST fail on "undocumented commands, parameters and test functions" (dev-only routes, seed endpoints, debug flags) reaching production builds. *SQ criterion 6 (SEAL-4); TR-03161-2 O.Source_6/O.Source_8.*

### Vulnerability handling and disclosure (CRA Annex I Part II, Art. 14; TR-03185 PROD.FIX)

- **TUV-VUL-01** — A published Coordinated Vulnerability Disclosure policy MUST exist (SECURITY.md + `/.well-known/security.txt` on operated instances) with a reporting contact and an encrypted channel. *CRA Annex I Part II(5)-(6); TR-03161-2 O.Arch_7; TR-03185 PROD.FIX.A.3.*
- **TUV-VUL-02** — Fixed vulnerabilities MUST be publicly disclosed with description, affected versions, severity and remediation guidance (GitHub Security Advisories; CSAF-compatible where feasible), and an online register of known vulnerabilities per operated service MUST be kept. *CRA Annex I Part II(4); C5 PSS-03; TR-03183-3.*
- **TUV-VUL-03** — An internal reporting runbook MUST implement the CRA Art. 14 clock (24 h early warning, 72 h notification, 14-day final report; severe incidents one month) via the single reporting platform, and name who of the 3 production-access holders triggers it. *CRA Art. 14, applicable from 11 Sept 2026.*
- **TUV-VUL-04** — The support period per release line and the minimum retention of published security updates (≥ 10 years or support period) MUST be declared in user-facing documentation. *CRA Art. 13(8)-(9), Annex II.*

### Operating instructions (SQ criterion 4, SEAL-4; CRA Annex II)

- **TUV-OPS-01** — The Deployment Security Guide MUST state the security requirements on the operating environment (TLS termination, network exposure, secrets, backups, ClamAV, resource limits), secure initial commissioning, how to install security updates, and secure decommissioning incl. data removal. *SQ criterion 4; CRA Annex II(8).*
- **TUV-OPS-02** — The shipped default configuration (compose, `.env.example`, config.json) MUST be secure by default; every deviation needed for development MUST be explicit and documented; a reset-to-secure path MUST exist. *CRA Annex I Part I 2(b); TR-03161-2 O.Data_1; extends ASVS V13.*
- **TUV-OPS-03** — Operated instances MUST log security-relevant events (auth success/failure, permission denials, org membership changes, uploads, admin actions) with synchronised time, ship them to a central store with access protection and tamper-evidence, and document the retention. *SQ product-specific requirement 5; CRA Annex I Part I 2(l); IT-Grundschutz OPS.1.1.5.A1/A4/A6/A10; C5 OPS-10…17; extends ASVS V16.*
- **TUV-OPS-04** — Container images MUST come from trusted sources, be updated on a defined cadence, run unprivileged with resource limits and immutable filesystems where possible, and store credentials outside the image. *IT-Grundschutz SYS.1.6.A6/A8/A14/A15/A17/A23; C5 PSS-11.*
- **TUV-OPS-05** — Users MUST be able to permanently delete all their data and settings and export them in a usable form. *CRA Annex I Part I 2(m); TR-03161-2 O.Data_15.*

### Change management (SQ criterion 7, SEAL-5; C5 DEV-03…09)

- **TUV-CHG-01** — Every change to production MUST be traceable to a reviewed, approved and tested commit; deployments MUST be logged; the change procedure MUST be documented with roles among the 3 production-access holders. *SQ criterion 7; C5 DEV-03/DEV-07/DEV-09; IT-Grundschutz OPS.1.1.3.*
- **TUV-CHG-02** — Changes to auth, permissions, upload or deployment MUST trigger a Review Run (already a map preference) and the Review Run MUST verify that the achieved security level has not decreased. *SQ criterion 7 ("must not lead to a reduction of the security level achieved"); CON.10.A12.*

### Penetration testing and verification (SQ criterion 5, SEAL-2; APP.3.1.A22)

- **TUV-PEN-01** — Each full Review Run MUST include a grey-box, documentation- and source-led penetration test of the local compose stack following the BSI five-phase model, covering the TÜViT web-pentest areas (authz/tenant isolation, input/output validation, authentication/session, misconfiguration, information disclosure, business logic, TLS), with results graded and re-tested. *SQ criterion 5; TÜViT web-pentest scope; APP.3.1.A22; ASVS 0x04 hybrid testing.*
- **TUV-PEN-02** — Vulnerability scans of container images and dependencies MUST run in CI and their reports MUST be attached to the Review Run as evidence. *C5 PSS-02/OPS-19; CRA Annex I Part II(3).*

### Organisation (Ring 4; ISO 27001 / TR-03183-H / C5)

- **TUV-ORG-01** — A minimal, written information-security policy set (access to production, secrets handling, incident handling, supplier/LLM-provider assessment) MUST exist and be reviewed yearly, structured so it can grow into an ISO 27001 ISMS if a Module H or C5 engagement is ever pursued. *TÜViT Module H prerequisite (ISO 27001 + TR-03183-H); C5 OIS/SP; CRA Art. 24(1) steward policy as floor.*

## Open questions

1. **Catalogue access.** Can the "SQ Requirements Catalog for Version 10.0" (doc. v2.9) be obtained from TÜViT under NDA or via the whitepaper request, and does it contain more than the seven criteria groups summarised on certificates? Would TÜViT accept an ASVS 5.0 L2 Control Register as the "published security requirements of recognized … bodies" for SQ criterion 1?
2. **TSS vs TPS.** open-dpp is both a product (software distributed to self-hosters) and three operated systems. Which object would TÜViT certify — the software version (TPS) or one operated instance (TSS)? The whitelabel per-customer instances would each be a separate TSS object; a TPS certificate follows the version, not the instance.
3. **Target SEAL.** SEAL-3 is the minimum for a certificate; SEAL-4 adds operating instructions and source-code analysis — both natural for an open-source project — at higher cost. Decide once the Control Register size is known.
4. **Accreditation.** SQ is run in TÜViT's "nicht akkreditierter Bereich". Does that matter for the customers/tenders that motivate the certificate, or would they rather ask for ISO 27001 (accredited) or a C5 attestation for the SaaS?
5. **CRA classification of open-dpp.** Manufacturer (monetised platform, Recital 15) vs open-source steward (Art. 24)? Is the operated SaaS "remote data processing" (Art. 3(2)) for self-hosted instances (e.g. if a hosted resolver/registry is ever required), or a pure NIS2 cloud service (Recital 12)? This decides whether Annex I Part II and Art. 14 bind the project or only inform it. Likely owned by the CRA research ticket.
6. **ESPR / DPP-specific security rules.** ESPR delegated acts and the CEN-CLC/JTC 24 DPP standards may impose their own requirements on DPP service providers (not researched here). Are they compatible with, or stricter than, the SQ/ASVS layer?
7. **Notified body status.** Has TÜViT (or any German body) been notified for the CRA since Chapter IV applied on 11 June 2026? Check NANDO for Regulation (EU) 2024/2847 before assuming a Module B/C route is available.
8. **TR-03161-2 version gap.** The BSI catalogue references ASVS 4.0; our backbone is 5.0. A TR-03161-2 → ASVS 5.0 crosswalk would let the register claim alignment with the one public German web-app catalogue — worth it only if a German assessor is expected to use it outside healthcare.
9. **Confidentiality of evaluation reports vs the map's disclosure plan.** SQ evaluation reports are TÜViT documents; the map keeps Review Run reports private for now — compatible, but decide what a future public "security statement" may quote.
10. **C5 for a 3-person operation.** C5:2026 is the operator-side yardstick German customers know; an ISAE 3000 attestation is auditor-driven and costly. Is a self-declared C5 mapping (YAML now available from BSI) a useful interim deliverable?
